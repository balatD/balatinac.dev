Surviving a TYPO3 v11 → v13 jump without downtime.

PublishedApr 18, 2026 Read time~9 min TYPO3UpgradeMariaDBDocker

Skipping a TYPO3 LTS is the kind of decision your future self either thanks you for or quietly resents for two months. Here's the path that worked, in the order it actually happened — including the four hours I lost to a TCA quirk that didn't deserve them.

Why we skipped v12

The honest answer: budget. The slightly more honest answer: every TYPO3 upgrade costs roughly the same fixed amount of human attention, regardless of how many majors you cross. Going v11 → v12 → v13 in two passes meant doing the audit, the staging dance, and the editor retraining twice. Going straight to v13 meant doing it once.

The catch is that you lose the cushion of an intermediate step where you can test theories. So you replace it with paranoia, which is cheaper.

The plan, in five lines

  1. Freeze content writes on staging, snapshot the database, run an extension audit.
  2. Spin up a parallel v13 stack against a copy of production data.
  3. Replay the upgrade scripts until they're a single idempotent shell file.
  4. Cut writes over to a buffer, run the real upgrade, validate, release writes.
  5. Watch logs. Drink coffee. Don't touch anything for 48 hours.

The extension audit

Before any code changed, we listed every installed extension across the four sites and graded each one. The grades were intentionally crude — I wanted decisions, not nuance:

  • keep — already v13-compatible, no action.
  • port — small patch needed; we'd own it.
  • replace — official replacement exists in core or a maintained alternative.
  • delete — nobody could explain what it did. Out it goes.

About 40% of installed extensions hit delete on the first pass. Roughly half of those got reinstated when an editor noticed something missing — but the audit forced the conversation, which was the point.

An upgrade is a great excuse to delete things you couldn't otherwise justify deleting.

Blue/green database, not blue/green app

Most "zero downtime" guides describe a blue/green app deploy and hand-wave the database. For TYPO3 the database is the migration: schema changes, content element renames, FAL references. The app side is comparatively easy.

So we inverted the usual setup. The new application stack ran against a replicated MariaDB; the old one stayed on the live primary. A small write-mirror service caught any new content during the cutover window and replayed it on the green side. When the parity report came back all-zeros for 48 hours, we flipped a single Nginx upstream:

# cutover.sh
ssh edge-01 "ln -sfn /etc/nginx/upstreams/v13 /etc/nginx/upstreams/active && nginx -s reload"
ssh edge-02 "ln -sfn /etc/nginx/upstreams/v13 /etc/nginx/upstreams/active && nginx -s reload"
# total downtime: ~0.4s per edge

No request was dropped. The writes that were in flight during the symlink swap got served by the v11 upstream and replayed forward by the mirror within 90 seconds.

The four hours I'll never get back

The bug was a custom TCA override on a content element that had been ported from v9 in 2020. In v13, a column type that used to be coerced silently now refuses to load if its config.eval contains a deprecated value. The error message did not mention TCA. It mentioned the cache.

I cleared every cache TYPO3 has — and TYPO3 has a lot of caches. I rebuilt Composer autoload. I bisected the database. I read the changelog twice. Eventually I diff'd the loaded TCA between v11 and v13, found one column with a different shape, deleted the override, and the whole platform booted in under a second.

The lesson is the lesson everyone learns: tail -f var/log/* is a habit, not a fallback.

What I'd do differently

  • Run the extension audit a month earlier. Two weeks isn't enough for editors to push back on the delete column.
  • Wire the parity report into a chat channel from day one. Watching numbers tick down to zero is more reassuring than any postmortem.
  • Schedule the cutover for Tuesday morning, not Friday night. The sleep difference is real.
  • Write the cutover script before you need it, then run it on staging until it's boring.

Closing

The upgrade itself shipped without an incident, the editors barely noticed, and the platform has been on v13 for six months without anyone needing to think about it. That's the only metric I cared about.
